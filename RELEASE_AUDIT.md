# Release Audit — Independent Final Verification

This is an independent, adversarial audit performed after the v1.0 production-readiness pass documented in `PROJECT_AUDIT.md`. Nothing in that document, or in any other doc in this repo, was trusted at face value. Every claim below was checked against the actual source, actual test runs, actual tool output, or an actual fresh measurement — performed by a mix of direct verification and four independent read-only subagents each scoped to a different slice of the repository (GUI, core library/security, documentation cross-check, tests + Flutter-SDK scope check).

**Method:** fresh `pytest`/`ruff`/`black`/`mypy` runs against current source (not reused from memory), direct file reads of every `src/` and `tests/` module, hand-built malformed-input probes against the parser, a from-scratch performance re-benchmark on a synthetic (non-personal) capture, and a line-by-line cross-check of every top-level doc against the code it describes.

---

## 1. Repository Overview

`revolt_ble_toolkit` is a Python 3.12 toolkit for reverse-engineering BLE traffic from Android HCI Snoop Logs, plus a PySide6 desktop GUI, a Bleak-based live BLE client, and a companion Flutter/Dart SDK (`flutter_sdk/`) for mobile. The Python side has zero runtime dependencies in its core library (parsers/analyzers/exporters); PySide6 and Bleak are opt-in extras. `flutter_sdk/` is out of scope for this audit's *changes* by long-standing project convention (never modified in this pass), but its existence claim was independently checked (see §2).

## 2. Verified Features

Everything below was independently confirmed against source, not copied from prior documentation:

- **HCI/ATT/GATT parsing pipeline** (`parsers.btsnoop`, `parsers.att`, `analyzers.gatt`) — real, tested, 96–100% covered.
- **Heuristic protocol classification & cross-capture comparison** (`analyzers.protocol`, `analyzers.compare`) — every classification carries a confidence score and a plain-English reason string; no bare labels found anywhere.
- **CLI** (`revolt-ble-toolkit parse|analyze|export|compare`) — smoke-tested live in this audit (`--version`, `--help`, and a real `parse` run against a synthetic capture all work exactly as documented).
- **Desktop GUI** — drag-and-drop, search/filter, click-to-seek timeline, Hex/ASCII/Statistics panes, a real (not stubbed) dark `QPalette` theme, and a `File` menu with Export Report..., Compare with..., a `QSettings`-backed Recent Captures list, and keyboard shortcuts (Ctrl+O/E/Shift+C/F/Q) — all independently confirmed present and wired to real logic, with file:line evidence, by a dedicated verification pass.
- **Live BLE client** (`live.RevoltLiveClient`) — tested against a fake Bleak backend built from the *actually-installed* `bleak==3.0.2` (confirmed via `pip show bleak` in this pass, not assumed).
- **Flutter SDK** (`flutter_sdk/`) — confirmed to be a real, non-trivial Dart package (not a stub/template): a ~243-line client mirroring the Python live client's protocol/reconnect philosophy, plus a genuinely runnable example app. Read-only scope check only, per project convention.
- **143/143 → 150/150 tests passing, 93% line coverage, 0 Ruff findings, 0 Black reformats, 0 MyPy errors** — all re-verified fresh in this pass, including `mypy` run against `src/` *and* `tests/` together (a stale, unused `mypy.overrides` entry for `tests.*` had been masking that tests weren't actually being strict-checked in the commonly-used `mypy src/` invocation; removed, and the one real error it uncovered was fixed — see §5).

## 3. Incorrect Claims Found

1. **"Measured, not guessed" performance numbers were measured against a real personal device's capture, not a reproducible one.** The 25.5 ms / 27.3 ms / 2.33 MiB figures in `KNOWN_LIMITATIONS.md` were real measurements, not fabricated — but the capture they came from was never part of the repo and can't be regenerated by another contributor. Superseded (see §7).
2. **GUI coverage gaps were overstated as "not meaningfully unit-testable without a running display."** This was true for `dragEnterEvent`/`dropEvent` (needs a real OS drag session) but false for the category-filter, row-selection, timeline-seek, and timeline-click-to-paint-event handlers — Qt's offscreen backend runs these correctly when fed a directly-constructed event. Tests now exist; the claim in `KNOWN_LIMITATIONS.md` has been corrected.
3. **README's "Project layout" tree omitted `live/models.py`.** Fixed.
4. **A stale `mypy` override for `tests.*`** referenced a relaxation that was, in the one place it would have mattered, hiding a real untyped test function rather than being genuinely unused. Both the override and the underlying untyped function are now resolved (see §5).
5. **`DEVELOPER_GUIDE.md` described `scratch/` as a legitimate, intentionally-lint-excluded artifact.** It was — and that sanctioned, unlinted, ungoverned status is exactly how a script containing real personal data ended up committed and pushed. Doc corrected; the practice is now explicitly discouraged (see §8).

No other numeric claim, file path, or class/function reference checked across `ARCHITECTURE.md`, `PIPELINE.md`, `DEVELOPER_GUIDE.md`, `ROADMAP.md`, `docs/hci_parser.md`, or `docs/att_parser.md` was found to be wrong.

## 4. Documentation Corrections

Applied this pass: `README.md` (live/ tree), `DEVELOPER_GUIDE.md` (scratch/ description + a warning about the incident in §8), `KNOWN_LIMITATIONS.md` (performance table replaced with synthetic/reproducible numbers + honest run-to-run variance; GUI coverage numbers corrected), `PROJECT_AUDIT.md` and `REMAINING_TASKS.md` (same performance numbers, GUI coverage numbers, test count, and a new "Fixed in the final release audit" bullet), `FINAL_STATUS.md` and `RELEASE_NOTES.md` (test count 100→150, coverage 86%→93%), `CHANGELOG.md` (updated test-count/coverage tally, added the timestamp-crash fix and the PII-removal entry).

## 5. Code Improvements Made

- **Fixed a real, previously-unknown crash bug:** `BtSnoopHciParser` raised an unhandled `OverflowError` on any record whose timestamp field was far enough from the real BTSnoop epoch offset to fall outside Python's representable `datetime` range — a zero-filled or corrupted timestamp field being entirely plausible corruption, not an adversarial edge case. It crashed the CLI with a raw traceback instead of the toolkit's own documented "log and skip" convention. Fixed in `parsers/btsnoop/parser.py`'s `_iter_packets`: the malformed record is now logged and skipped, and parsing continues with the rest of the file. A regression test (`test_out_of_range_timestamp_is_skipped_not_crashed`) was added.
- **Removed a stale, actually-load-bearing-until-now `[[tool.mypy.overrides]]` section** (`module = "tests.*"`) and fixed the one real untyped-function error it uncovered (`tests/test_live/test_client.py`'s `_FakeServices.__iter__`), so `mypy` now passes strict with zero overrides across both `src/` and `tests/`.
- **Removed two now-dangling `pyproject.toml` lint-exclude entries** (`extend-exclude = ["scratch"]` for Ruff, `extend-exclude = "^/scratch/"` for Black) pointing at a directory that no longer exists (see §8).
- **Added `.gitignore` entries** for `output/`, `*.zip`, and `scratch/` so this class of leak can't recur silently.

## 6. Test Improvements

- 1 new regression test for the timestamp-`OverflowError` fix.
- 3 new `MainWindow` tests exercising the category-filter, row-selection, and timeline-seek handlers directly (previously wired but untested).
- 5 new `TimelineWidget`/formatting tests: `format_ascii`'s empty-input branch, a real `mousePressEvent`-driven click test (asserting the correct bucket/packet index is emitted), a no-packets click that correctly emits nothing, and a `paintEvent` smoke test via `.repaint()`.
- Net effect: 143 → **150** tests, `gui/main_window.py` 89% → **95%**, `gui/widgets.py` 86% → **91%**, overall **93%** (up from 92% before this pass, 86% at the true start of the v1.0 effort).
- **Confirmed test-suite integrity independently:** `pytest --collect-only` collects all 150 items with zero collection errors; no vacuous tests found (every test asserts on real computed output); `tests/conftest.py`'s one autouse fixture (`_reset_settings_cache`) is genuinely needed by the config env-override tests.

## 7. Performance Results

Re-benchmarked from scratch this pass, against a **synthetic, reproducible** 174.7 KiB / 4,706-packet capture (built with the project's own `tests/test_parsers/fixtures.py` helpers — no real device data), because the previous numbers in `KNOWN_LIMITATIONS.md`, while genuinely measured, were tied to a real personal bugreport that was never in the repo and is not reproducible by anyone else. Methodology: wall time is best-of-5 across 3 separate process runs with console logging disabled (log I/O during a timed loop distorts results the same way `tracemalloc` does); peak memory is from a separate `tracemalloc`-instrumented run.

| Stage | Wall time (range across 3 runs) |
|---|---|
| HCI parse | 40–64 ms |
| ATT decode | 15–33 ms |
| GATT discovery | 1–2 ms |
| Protocol classification | 16–31 ms |
| **Full pipeline** | **72–122 ms** |
| Full export (4 files) | 113–164 ms |
| Peak memory | 3.11 MiB (stable across all 3 runs) |

The ~2x run-to-run spread is real, disclosed variance from an ordinary Windows dev machine under normal background load — reported honestly rather than cherry-picking one run. Peak memory is rock-stable regardless. Extrapolated to a 1 GiB capture: ~12 minutes, ~18 GiB peak memory (this is the previously-projected "large-capture" concern; no capture near that scale has ever been available to actually test against — see `REMAINING_TASKS.md`).

## 8. Security Findings

**Critical (real personal data, already found and remediated mid-audit):** the repo contained a committed, ad-hoc script (`scratch/generate_all_outputs.py`) and its generated output (`output/`, `output.zip`) derived from a real Android bugreport. The output contained a real-looking **IMEI**, a real-looking **SIM ICCID/serial**, and what decodes to a real **device pairing token**, plus a local Windows username in a file path. This landed in commit `ed1fde2` and was already reachable from `origin/main` and 4 other remote branches on `github.com/MannDangrechiya/revolt_ble_toolkit` — i.e., if that repository is or was public, this data may already be exposed, not merely "at risk." Per explicit user decision mid-audit, the files were removed from the working tree (staged, not committed) and `pyproject.toml`'s now-dangling lint-exclusions for the deleted `scratch/` directory were cleaned up; **a git-history scrub across all 5 branches is a separate, deliberate decision the repo owner still needs to make** — this audit did not perform one, and did not force-push or rewrite history. This also directly contradicted the project's own "never present a guessed field as fact" principle: the removed `output/protocol.md` stated decoded telemetry fields as flat fact with no confidence score, unlike everything else in the actual, tested codebase.

**Real, fixed crash bug:** see §5 (`OverflowError` on out-of-range timestamps) — this is the one genuine "malformed input crashes the tool" finding; every other malformed-input path checked (truncated file header, truncated record header, truncated packet data, truncated ACL header, undersized GATT discovery entries) already fails gracefully via a clean `ParsingError`/log-and-skip, confirmed by hand-building malformed files and running them through the real parser.

**Judged and not flagged as a vulnerability:** `generate_capture_report`'s unvalidated `out_dir` argument (a user could pass `../../etc`) — for a local desktop/CLI tool where the only "attacker" is the user's own argument or file-picker selection, letting them write to a path they name is expected behavior, not a sandbox escape. No shell/eval injection surface exists anywhere in the CLI or GUI (`app.exec()`/`dialog.exec()` are Qt's event-loop methods, unrelated to Python `exec`).

## 9. Protocol Verification

Every heuristic classification in `analyzers.protocol` and `analyzers.compare` carries a numeric confidence score and a plain-English reason string — confirmed by direct read of every branch in `_correlate`/`ProtocolAnalyzer.classify`. No bare "this is battery/temperature/GPS" label exists without a confidence + reason attached. The magic-number thresholds behind these heuristics (e.g. `cv < 0.3`, entropy `>= 3.5`, small-enum cutoffs) are inherent to a heuristic classifier by design, but are not individually commented with why that specific number was chosen — a minor documentation gap, not a "guessed-as-fact" violation, since every one of them is already surfaced to the user as a scored guess, not a fact. Separately, the committed `output/` artifacts removed in §8 were the one place in the entire repo that violated this principle (protocol facts stated flatly, no confidence) — and they were never part of the actual, tested `revolt_ble_toolkit` package to begin with; they were an ad-hoc script's output sitting alongside it.

## 10. Remaining Limitations

- **Git history still contains the removed personal data** on 5 branches until the repo owner decides on and executes a history rewrite (out of scope for this audit to perform unilaterally).
- **`gui/app.py` (dark theme + entry point) has 0% test coverage.** Real, working code, verified by direct read, but no `tests/test_gui/test_app.py` exists.
- **`gui/main_window.py`'s `dragEnterEvent`/`dropEvent`** (11 remaining missing lines) genuinely need a real OS drag-and-drop session to exercise; not fixed this pass, correctly judged not worth faking.
- **Heuristic classification accuracy on other devices/firmware is unverified** — unchanged from prior audits; this needs more real captures, not more code.
- **No real-hardware validation of the live BLE client** — unchanged; `bleak==3.0.2` is confirmed actually installed and tested against, but no physical adapter was available in this environment.
- **`flutter_sdk/`** was scope-checked (confirmed real, non-trivial) but not deep-audited — out of scope per standing project convention, and its own docs remain the source of truth for its state.
- **Streaming/lazy pipeline for very large (~1 GiB) captures** remains undone, correctly, since no capture near that scale has ever existed to justify the rewrite risk.

## 11. Release Readiness

The Python toolkit itself (`src/revolt_ble_toolkit/`) is in genuinely good shape: 150/150 tests passing, 93% coverage, zero lint/format/type errors verified fresh (not reused), one real crash bug found and fixed by this independent pass, and no other unhandled-crash path found across a deliberate hand-built malformed-input sweep. Every doc claim checked resolved to true after the corrections in §3–4.

**The one blocking item for a *public* release is not code — it's the git history exposure in §8.** Shipping this repository publicly today, as-is, would publish real personal device data (IMEI, SIM serial, pairing token) that's reachable from 5 branches. The working-tree files are gone; the history is not. This is a decision for the repo owner (rewrite history + force-push + consider the token/IMEI already-compromised if the repo was ever public, vs. accept the exposure), not something this audit can or should decide unilaterally.

## 12. Overall Completion Percentage

**93%**, based only on: 93% measured line coverage, 150/150 passing tests, 0 static-analysis errors, and every feature claim in this report independently confirmed against source rather than inferred. This number intentionally tracks the measured test-coverage figure rather than a subjective "feature completeness" estimate, since coverage is the one number here that's directly, mechanically verifiable.

## 13. Honest Production Readiness Assessment

**Code: ready.** **Repository: not yet ready for public release** until the git-history question in §8 is resolved by the repo owner. Everything else — the toolkit's actual parsing/analysis/GUI/CLI functionality, its test suite, its lint/type/format cleanliness, its documentation accuracy — held up under an adversarial, trust-nothing re-verification. The one real code bug found (§5) was a genuine gap in prior test coverage, not a sign of broader rot; it was fixed and regression-tested in this same pass. The one real blocker is a data-hygiene incident, not a software defect, and it is squarely the kind of decision (history rewrite scope, credential-rotation need, whether the GitHub repo was ever actually public) that requires the repo owner's judgment, not an automated audit's.
